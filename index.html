The shared principle

The agent asks. A console you hold answers.

In-agent approval is a convenience; a separate approval process is a boundary. The credentials and the only connections live in a console that runs under its own OS account, in a terminal you keep in view.

🗄️ Database

MariaDB · MySQL · PostgreSQL · SQLite

  1. Ask. The agent proposes a query, a read or a plan. It has no password and opens no connection.
  2. Approve. The console checks it, shows you exactly what will run and waits for your approval. No answer means denied.
  3. Answer. Only the answer goes back: masked rows, masked messages, or a 1 / 0. The audit log keeps who asked what.

The approval hub

Every lock, answered from one place.

With lockhub, a lock no longer needs you at its own terminal. It sends the hub a signed ticket with the masked screen of the request; you answer from a facade; the hub signs your decision, bound to the exact plan you saw, and the lock runs only on that signed decision. The hub never runs a request, never sees its results and never sees values in clear. The lox CLI declares the hub and a workspace's locks, reviews every change with you, and runs them with Docker Compose.

  • Facades. Your terminal (lox approve), the lea deck, Slack, Telegram, and a paired phone (an installable web app the hub serves, with optional Web Push). Each risk class goes only where it is safe to answer (see “routing” below); a workspace can narrow the routing, never widen it.
  • Clear values. Screens are masked everywhere. With reveal: true on a lock, o (or Ctrl-O, where the terminal passes it) in lox approve or the deck shows a ticket's clear values, sealed by the lock to that facade: the hub relays ciphertext. Never on chat.
  • Phones. With devices: true a lock pins the paired phones, and a decision taken on a phone is signed by the phone itself (WebAuthn): the hub's key alone cannot pass for it. require_device lists the risk classes only a phone's signature may approve; seal_clear seals the clear screen to the phones.
  • lea. lea follows the hub by default (LEA_HUB=1): an agent whose Lock call waits for a decision is suspended until it comes, and the deck shows and answers the hub's tickets. lea mounts .lockfamily/ read-only in its agents and gives them the locks' sockets named in .lockfamily/up.json; no agent reaches the hub.

Linux and macOS · Docker and cosign · lockhub v0.2 pre-release · locksql v0.11 or later

# 1. Install the lox CLI (checks the release signature with cosign)
curl -fsSL https://lockfamily.dev/install.sh | sh
# 2. In your workspace (lea's projects directory): a locksql lock, pinned by
#    digest to its latest signed release; the hub's image is pinned with it
cd ~/projects
lox add locksql crm
# 3. The lock's profile, in the workspace
mkdir -p .locksql
cat > .locksql/config.toml <<'TOML'
[profiles.crm]
engine = "postgres"
host = "host.docker.internal"
port = 5432
user = "ro"
database = "app"
tls = "disable"          # host.docker.internal is not loopback: TLS defaults to verify-full
TOML
chmod -R go-w .locksql   # lox up refuses a profile others can write
# 4. Review everything, then start the hub and the lock
lox up
# 5. The console's start-up questions (policy, password); detach: Ctrl-P Ctrl-Q
lox attach crm
# 6. Answer tickets here, or from the lea deck
lox approve

On Linux the database must listen on the Docker bridge, not only on 127.0.0.1. Then ask an agent that lea started after lox up: “how many orders were placed yesterday?”. Its query waits on the hub for your y. lox doctor checks the setup and changes nothing. How lox up and lea fit

lox add and lox import only edit .lockfamily/lockfamily.yaml: the next lox up reviews every change with you

lox add TYPE INSTANCE [--version vX.Y.Z | --image REF] [--profile P] [--hub-image REF]
                  # locksql, lockmq, lockfile, lockhttp: pinned by digest, cosign-verified
lox add slack --team T… --channel C… --user U…    # tokens asked at the terminal
lox add telegram --chat ID --from ID               # bot token asked at the terminal
lox import [SUB…]        # merge sub-projects' lockfamily.yaml, strictest routing kept
lox up [--dry-run] [--pin sha256:DIGEST] [--rotate hub|INSTANCE|all]
                  # review, then start; --pin restores a hub version by digest;
                  # --rotate (repeatable) replaces the hub's or a lock's key
lox attach INSTANCE      # a console's start-up questions; detach: Ctrl-P Ctrl-Q
lox approve [--once]     # y, n reason, s, q; o (Ctrl-O + Enter, not macOS): clear values;
                  # r on an expired ticket: approve again
lox mobile pair --name phone    # one-time code, confirmed at this terminal; then lox up
lox mobile list
lox mobile revoke NAME   # then lox up
lox doctor               # hub, locks, keys, socket, network; changes nothing
lox audit verify --data DIR --hub-key-file FILE [--lock INSTANCE=PATH] [--anchors FILE]
                  # the hub's audit chain and every decision's signature

The workspace commands take --file to name another lockfamily.yaml. lockhub

<workspace>/.lockfamily/lockfamily.yaml · lea's agents only read it there · a lock's target, production flag and credentials stay in its own profile

version: 1
hub:
  image: ghcr.io/davidgodefroid/lockhub@sha256:…
  facades: [tty, deck, mobile, slack]   # default: tty, deck
  routing:
    crm: [tty, deck, mobile]            # narrows an instance, never widens
  slack:
    team: T0123
    channel: C0123
    users: [U0123]
  mobile:
    origin: https://hub.example.ts.net  # your TLS proxy or tunnel to 127.0.0.1:8444
    seal_clear: true                    # clear values, end to end to the phone
    require_device: [prod-write]        # only a phone's own signature approves these
    push: true                          # Web Push, no payload
locks:
  crm:
    type: locksql
    image: ghcr.io/davidgodefroid/locksql@sha256:…
    devices: true                       # pins the paired phones
    reveal: true                        # o / Ctrl-O on the terminal and the deck

lox up writes .lockfamily/up.json for lea and keeps the hub's data, keys and audit log under $XDG_STATE_HOME/lockfamily/ (default ~/.local/state/lockfamily/), out of the workspace. A lockfamily.yaml at the workspace's root (the older layout) is still read, with a warning, until .lockfamily/ exists.

Who may answer which risk class: the hub enforces it, whatever a facade does

read, read-pii, writeyesyesyes, never a production ticket
prod-write, policy-loosenyesyesno
unlockyesnono
clear valueson demand: o / Ctrl-O (reveal: true)sealed to it (seal_clear)never

A chat facade never answers a production ticket, whatever its risk class. Chat facades show masked screens only, every agent-supplied string escaped: a chat account is only as safe as the devices signed in to it.

Quick start

Pick one. Running in a few commands.

Linux and macOS (Windows through WSL2), or Docker · MariaDB, MySQL, PostgreSQL, SQLite · v0.8 pre-release

# 1. Install
curl -fsSL https://raw.githubusercontent.com/DavidGodefroid/locksql/main/scripts/install.sh | sh
# 2. In your project: the console account, your agents, a database profile
locksql setup
# 3. In a session of the locksql account, start the console and keep it open
locksql console --project DIR

Then ask your agent: “how many orders were placed yesterday?”. Install options, checksums and signatures

Linux and macOS · RabbitMQ 3.13 and 4.x · v0.1 pre-release

# 1. Install
curl -fsSL https://raw.githubusercontent.com/DavidGodefroid/lockmq/main/scripts/install.sh | sh
# 2. Separate the console from the agent (once per machine)
lockmq install
# 3. In your project: a broker profile and your agents
lockmq setup
lockmq init
# 4. In a session of the lockmq account, start the console and keep it open
lockmq console --profile dev --project DIR

Usage guide

Console on Linux (Landlock and seccomp sandbox the plugins); agent side on Linux and macOS · v0.2 pre-release

# 1. Install (checks the release signature with cosign)
curl -fsSL https://raw.githubusercontent.com/DavidGodefroid/lockfile/main/scripts/install.sh -o install.sh
sh install.sh
# 2. The separated setup: console account `lockfile`
sudo lockfile install
# 3. In the lockfile account: a source, two plugins, the console
lockfile profile add samples --source local --path /srv/samples --prefix invoices/
lockfile plugin install format.is-pdf@1.0.0
lockfile console --profile samples
# 4. In your account: wire your agent, then ask
lockfile init claude

Know the limits

All of them, the hub included, are pre-release. The console is the enforcement point; skills and tool descriptions only guide the agent. Masking is best effort. Each project documents what the agent can see and its residual risks in its security model: locksql, lockmq, lockfile, lockhttp, lea. Chat facades never answer production tickets: a chat account is only as safe as the devices signed in to it.
