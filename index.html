Harness security for AI agents · open source · Apache 2.0

Your agent asks. A Lock holds the keys. You sign in lox run.

Claude Code, Codex, lea or any MCP client works on your SQL databases, RabbitMQ, files, logs and outbound HTTP(S) through a Lock. The Lock keeps the credentials and the only connection, in a container the agent cannot reach, and masks every value it returns. Each request becomes a masked ticket: reads pass by a rule, while a connection, a write or DDL waits for your y in lox run, a terminal outside the agent's harness.

An agent harness is the program that runs a model as an agent and hands it tools; harness security is the layer around it, separate from the model's own guardrails because it holds whatever the model is talked into. Every approval is answered outside the harness, so an agent can never answer its own.

  1. brew trust davidgodefroid/tap and brew install davidgodefroid/tap/lockfamily
  2. lox add locksql in your project (or lockmq, lockfile, lockhttp, locklog)
  3. lox run in a terminal of its own, while your agent (claude, Codex or lea) works in another. Quick start

01

One write, from the agent's request to your signature

In-agent approval is a convenience; an approval outside the harness is a boundary. Here is what happens to one UPDATE, line by line, as the audit log records it. Each Lock reaches only the endpoints of its reviewed profile, and decisions can also come from an auto rule, lox approve, Slack, Telegram or a paired phone.

  1. 14:03:01agent

    Asks its Lock client, an MCP server with no credential and no connection, to run UPDATE orders SET status = 'paid' WHERE id = 41277. The client passes it over a socket to the Lock.

  2. 14:03:01lock

    In its own container, it parses the statement, classes it a write and masks every value: status = ‹p***(4)›. It runs nothing yet, and sends the hub a ticket with that masked screen.

  3. 14:03:01hub

    Queues the ticket for lox run. The agent has no route to it; it never runs a request and never sees a result or a value in clear.

  4. 14:03:02you

    In lox run, your own terminal. Auto mode passes reads by rule; a write is always asked, so the bell rings. You read the masked screen and press y.

  5. 14:03:04hub

    Signs the decision, bound to that exact plan and naming who decided: you, not a rule.

  6. 14:03:04lock

    Checks the signature, runs the UPDATE, and returns 1 row updated to the agent. On n, no answer, or a closed lox run, nothing runs and the agent only learns it was denied.

  7. lateraudit

    lox audit lists the line: who asked, the masked request, who or which rule decided, and the outcome.

Shared core

lockkit

The console, hub-attached only, its isolated account and socket, policies the AI may tighten and only you loosen, the approval screen and the hub's tickets, the audit log, credentials kept in the console (an ask password typed at the first connection in lox run and sealed to the Lock, or a login read from HashiCorp Vault), personal-data masks, MCP and agent wiring.

One hub runs every Lock. lox run starts the hub and each Lock's console with Docker Compose; there is no standalone console. Each Lock but lockhttp sits on an internal network, behind an egress gateway that reaches only its reviewed profile's endpoints: no internet, cloud metadata or other host port. lea's agents reach the Locks' sockets through .lockfamily/up.json, and so does any Claude Code on the host, through each Lock's launcher (locksql mcp, …); no agent reaches the hub. lea is optional (claude works too), except for lockhttp, whose gate runs beside lea's proxy.

03

The hub: every Lock's tickets, answered from one place

  • locksql
  • lockmq
  • lockfile
  • lockhttp
  • locklog

lockhub

queues masked tickets
signs decisions
runs nothing

  • lox run your terminal
  • lox approve
  • Slack, Telegram
  • a paired phone

Every Lock runs attached to lockhub. Its console holds the credentials and checks each request, then sends the hub a signed ticket with the masked screen; lox run decides it; the hub signs the decision, bound to the exact plan, and the Lock runs only on that signed decision. The hub never runs a request, never sees its results and never sees values in clear. The lox CLI sets each source up (lox add), reviews every change with you, runs the hub and the Locks with Docker Compose and serves the decisions (lox run), and lists what happened (lox audit).

  • lox run. The one terminal you keep open, outside lea and any agent harness. It shows every ticket and decision live, masked, and runs in auto mode by default: reads are approved by the rule, writes and DDL are asked every time, a connection once per profile per session (an ask password is typed there and sealed to the Lock), a new lockhttp endpoint once per session. locksql v0.17.0 and lockmq v0.8.0 take auto rules per profile (auto, ask or deny). Shift+Tab switches to manual; the bell rings only for a question; quitting fails closed.
  • Other facades. lox approve, Slack, Telegram, and a paired phone (an installable web app the hub serves, with optional Web Push). Each risk class goes only where it is safe to answer (see “routing” below); a workspace can narrow the routing, never widen it.
  • Clear values. Screens are masked everywhere. With reveal: true on a lock, o (or Ctrl-O, where the terminal passes it) in lox approve shows a ticket's clear values, sealed by the lock to that facade: the hub relays ciphertext. Never on chat.
  • Phones. With devices: true a lock pins the paired phones, and a decision taken on a phone is signed by the phone itself (WebAuthn): the hub's key alone cannot pass for it. require_device lists the risk classes only a phone's signature may approve; seal_clear seals the clear screen to the phones.
  • lea. lea v0.9.0 no longer handles approvals: it starts no hub and shows no ticket. When the projects directory declares Locks and no lox run serves them, lea says to run it, and the agents' requests wait at the hub. lea mounts .lockfamily/ read-only in its agents and gives them the Locks' sockets named in .lockfamily/up.json. No agent reaches the hub.
  • Host agents. Any Claude Code on the host reaches the same Locks: each Lock's launcher, as .mcp.json starts it (locksql mcp, lockmq mcp, lockfile mcp, locklog mcp), finds the nearest .lockfamily/up.json up from the working directory (the project or a parent) and mounts the Lock's socket read-only once Docker confirms it is lox run's. Approve in lox run.

What lox add locksql runs for you, by hand, with locksql · Linux and macOS · Docker and cosign · lockhub v0.10.0 · locksql v0.17.0

# 1. In the project: Claude Code's files (its MCP server is `locksql mcp`),
#    a database profile (engine, host, TLS, where the password comes from;
#    never the password), then doctor --fix (.locksql/ as lox run reads it)
cd ~/projects            # your project (with lea: lea's projects directory)
locksql init claude
locksql profile add --profile orders
locksql doctor --fix --yes
# 2. Declare the lock: pinned by digest to its latest signed release;
#    the hub's image is pinned with it
lox add locksql orders --profile orders
# 3. In a terminal of its own, outside the agent: review everything,
#    start the hub and the console, then serve the decisions
lox run

A database on this machine is host.docker.internal; on Linux it must listen on the Docker bridge, not only on 127.0.0.1. For lea's agents, the lock names your uid (allowed_uids: [1000], id -u, in lockfamily.yaml; lox add adds it when lea is installed). Then ask an agent: “how many orders were placed yesterday?”. lox run asks you once for the connection, then the read runs, masked; a write waits for your y every time. lox doctor checks the setup, the egress allowlist included, and changes nothing. How lox run, lea and host agents fit

lockhub v0.10.0 · lox add TYPE INSTANCE and lox import only edit .lockfamily/lockfamily.yaml: the next lox run reviews every change with you

lox run [--manual] [--no-start] [--no-upgrade] [--review] [-v]
        [--pin sha256:DIGEST] [--rotate hub|INSTANCE|all]
                  # review, start the hub and the locks, then serve decisions live:
                  # auto mode (Shift+Tab: manual), a: the audit, q q: quit (fail closed);
                  # --no-start: serve only; --no-upgrade: keep the pinned images;
                  # --review: everything, line by line; -v: cosign's and docker's output;
                  # --pin: the hub image by digest; --rotate: replace a key first
lox init [--review] [--hub-image REF]
                  # start the project's hub alone; asks nothing; hints at the sources its files name
lox add TYPE      # locksql, lockmq, lockfile, lockhttp, locklog: its questions, profile, declaration,
                  # a short review, the console's questions; nothing kept on a failure
lox add TYPE INSTANCE [--version vX.Y.Z | --image REF] [--profile P] [--hub-image REF]
                  # the older form: only declares the lock, pinned by digest, cosign-verified
lox add slack --team T… --channel C… --user U…    # tokens asked at the terminal
lox add telegram --chat ID --from ID               # bot token asked at the terminal
lox remove NAME [--purge] # take a lock out after one review; its profile stays unless --purge
lox import [SUB…]        # merge sub-projects' lockfamily.yaml, strictest routing kept
lox attach INSTANCE      # a console's start-up questions; detach: Ctrl-P Ctrl-Q
lox approve [--once]     # y, n reason, s, q; o (Ctrl-O + Enter, not macOS): clear values;
                  # r on an expired ticket: approve again
lox mobile pair --name phone    # one-time code, confirmed at this terminal
lox mobile list
lox mobile revoke NAME
lox doctor               # hub, locks, keys, egress allowlists, socket, network; changes nothing
lox audit [show ID]      # every exchange: masked request, rule or human, outcome
lox audit verify --data DIR --hub-key-file FILE [--lock INSTANCE=PATH] [--anchors FILE]
                  # the hub's audit chain and every decision's signature

The workspace commands take --file to name another lockfamily.yaml. lox up is deprecated: it says to use lox run. lockhub

<workspace>/.lockfamily/lockfamily.yaml · lea's agents only read it there · a lock's target, production flag and credentials stay in its own profile

version: 1
hub:
  image: ghcr.io/davidgodefroid/lockhub@sha256:…
  facades: [tty, mobile, slack]
  routing:
    orders: [tty, mobile]               # narrows an instance, never widens
  slack:
    team: T0123
    channel: C0123
    users: [U0123]
  mobile:
    origin: https://hub.example.ts.net  # your TLS proxy or tunnel to 127.0.0.1:8444
    seal_clear: true                    # clear values, end to end to the phone
    require_device: [prod-write]        # only a phone's own signature approves these
    push: true                          # Web Push, no payload
locks:
  orders:
    type: locksql
    image: ghcr.io/davidgodefroid/locksql@sha256:…
    profile: orders                     # the profile the console serves
    allowed_uids: [1000]                # id -u of the account that runs lea
    devices: true                       # pins the paired phones
    reveal: true                        # o / Ctrl-O in lox approve

lox run writes .lockfamily/up.json for lea and the launchers and keeps the hub's data, keys and audit log under $XDG_STATE_HOME/lockfamily/ (default ~/.local/state/lockfamily/), out of the workspace. A lockfamily.yaml at the workspace's root (the older layout) is still read, with a warning, until .lockfamily/ exists.

Who may answer which risk class: the hub enforces it, whatever a facade does

Risk classTerminalPhoneSlack, Telegram
read, read-pii, writeyesyesyes, never a production ticket
prod-write, policy-loosenyesyesno
unlockyesnono

A chat facade never answers a production ticket, whatever its risk class. Chat facades show masked screens only, every agent-supplied string escaped: a chat account is only as safe as the devices signed in to it.

04

Install, add your sources, keep lox run open

Linux and macOS · Docker · lockhub v0.10.0, lea v0.11.0

# 1. Install the Lock Family: lox, lea, the Locks' launchers and cosign
#    (Homebrew asks you to trust a third-party tap once)
brew trust davidgodefroid/tap
brew install davidgodefroid/tap/lockfamily
#    or into ~/.local/bin, at the tap's versions, each verified with cosign:
#    curl -fsSL https://lockfamily.dev/install.sh | sh
# 2. In your project (with lea: lea's projects directory), each source, one at a time
cd ~/projects
lox add locksql          # or lockmq, lockfile, lockhttp, locklog
# 3. In a terminal of its own, outside the agent: approvals live here
lox run
# 4. Your agent, in another terminal
claude                   # or Codex, or lea

lox add TYPE sets one source up and creates .lockfamily/lockfamily.yaml when it does not exist yet: its questions, the launcher's profile add, init claude and doctor, a short review of that Lock, and the console's own questions; a failure, an n or Ctrl-C keeps nothing. lox init starts the hub alone first, if you prefer: it asks nothing and lists the data sources the project's files name (.env*, compose*.yaml, config/: hints only, never a secret). A Lock added while lea runs reaches it at lea's next start: lea stop, then lea. Where to run them: for lea, in its projects directory, the only place lea reads .lockfamily/up.json; for a plain claude, in the project or any parent, since each Lock's launcher looks up from the working directory. lockfile is Linux only; locklog's local log sources are Linux only (on macOS it reads the remote sources: Loki, Elasticsearch/OpenSearch). lox add · by hand

Known limits

All of them, the hub included, are before v1: lockhttp v0.8.0 is a pre-release; lockhub v0.10.0, lea v0.11.0, locksql v0.17.0, lockmq v0.8.0, lockfile v0.8.0, locklog v0.2.1 and lockkit v0.13.1 may still change. Auto mode approves reads by rule: switch to manual (Shift+Tab) to answer every ticket yourself. The console is the enforcement point and runs hub-attached only; skills and tool descriptions only guide the agent. Masking is best effort. Each project documents what the agent can see and its residual risks in its security model: locksql, lockmq, lockfile, lockhttp, locklog, lea. Chat facades never answer production tickets: a chat account is only as safe as the devices signed in to it.
