The shared principle

The agent asks. The console checks. You answer on the hub.

In-agent approval is a convenience; a separate approval process is a boundary. The credentials and the only connections live in a Lock's console, in a container of its own that the agent cannot reach. The console sends what it would run, masked, to the approval hub, and runs it only on the decision you take there: in a terminal, the lea deck, Slack, Telegram or a paired phone.

  1. Ask. The agent proposes a query, a read or a plan. It has no password and opens no connection.
  2. Approve. The console checks it and sends the hub a signed ticket with the masked screen of exactly what will run. You answer from lox approve, the lea deck, chat or your phone; the console runs it only on the hub's signed decision, bound to that plan. No answer means denied.
  3. Answer. Only the answer goes back: masked rows, masked messages, or a 1 / 0. The audit log keeps who asked what.

⚙︎

lockkit

The console, hub-attached only, its isolated account and socket, policies the AI may tighten and only you loosen, the approval screen and the hub's tickets, the audit log, credentials asked at the console's start, masked (Vault: not yet under lox up), personal-data masks, MCP and agent wiring.

One hub runs every Lock. lox up starts the hub and each Lock's console with Docker Compose; there is no standalone console. lea's agents reach the Locks' sockets through .lockfamily/up.json, and so does any Claude Code on the host, through each Lock's launcher (locksql mcp, …); no agent reaches the hub. lea is optional (claude and lox approve work too), except for lockhttp, whose gate runs beside lea's proxy.

The approval hub

Every lock, answered from one place.

Every Lock runs attached to lockhub. Its console holds the credentials and checks each request, then sends the hub a signed ticket with the masked screen; you answer from a facade; the hub signs your decision, bound to the exact plan you saw, and the Lock runs only on that signed decision. The hub never runs a request, never sees its results and never sees values in clear. The lox CLI starts a project's hub (lea does it for you; lox init without lea), sets each source up (lox add), reviews every change with you, and runs them with Docker Compose (lox up).

  • Facades. Your terminal (lox approve), the lea deck, Slack, Telegram, and a paired phone (an installable web app the hub serves, with optional Web Push). Each risk class goes only where it is safe to answer (see “routing” below); a workspace can narrow the routing, never widen it.
  • Clear values. Screens are masked everywhere. With reveal: true on a lock, o (or Ctrl-O, where the terminal passes it) in lox approve or the deck shows a ticket's clear values, sealed by the lock to that facade: the hub relays ciphertext. Never on chat.
  • Phones. With devices: true a lock pins the paired phones, and a decision taken on a phone is signed by the phone itself (WebAuthn): the hub's key alone cannot pass for it. require_device lists the risk classes only a phone's signature may approve; seal_clear seals the clear screen to the phones.
  • lea. lea v0.4.0 follows the hub by default (LEA_HUB=1): an agent whose Lock call waits for a decision is suspended until it comes, and the deck shows and answers the hub's tickets. lea mounts .lockfamily/ read-only in its agents and gives them the Locks' sockets named in .lockfamily/up.json; without it, lea says to run lox up. No agent reaches the hub.
  • Host agents. Any Claude Code on the host reaches the same Locks: each Lock's launcher, as .mcp.json starts it (locksql mcp, lockmq mcp, lockfile mcp), finds the nearest .lockfamily/up.json up from the working directory (the project or a parent) and mounts the Lock's socket read-only once Docker confirms it is lox up's. Approve with lox approve.

What lox add locksql runs for you, by hand, with locksql · Linux and macOS · Docker and cosign · lockhub v0.4.0 pre-release · locksql v0.13.1

# 1. In the project: Claude Code's files (its MCP server is `locksql mcp`),
#    a database profile (engine, host, TLS, where the password comes from;
#    never the password), then doctor --fix (.locksql/ as lox up reads it)
cd ~/projects            # lea's projects directory (plain claude: your project)
locksql init claude
locksql profile add --profile orders
locksql doctor --fix --yes
# 2. Declare the lock: pinned by digest to its latest signed release;
#    the hub's image is pinned with it
lox add locksql orders --profile orders
# 3. Review everything, then start the hub and the console
lox up
# 4. The console's start-up questions (policy, masked password);
#    detach with Ctrl-P Ctrl-Q once it says Listening
lox attach orders
# 5. Answer tickets here, or from the lea deck
lox approve

A database on this machine is host.docker.internal; on Linux it must listen on the Docker bridge, not only on 127.0.0.1. For lea's agents, the lock names your uid (allowed_uids: [1000], id -u, in lockfamily.yaml; lox add adds it when lea is installed). Then ask an agent: “how many orders were placed yesterday?”. Its query waits on the hub for your y. lox doctor checks the setup and changes nothing. How lox up, lea and host agents fit

lockhub v0.4.0 · lox add and lox import only edit .lockfamily/lockfamily.yaml: the next lox up reviews every change with you

lox init [--review] [--hub-image REF]
                  # start the project's hub; asks nothing; hints at the sources its files name
lox add TYPE      # locksql, lockmq, lockfile, lockhttp: its questions, profile, declaration,
                  # a short review, the console's questions; nothing kept on a failure
lox add TYPE INSTANCE [--version vX.Y.Z | --image REF] [--profile P] [--hub-image REF]
                  # the older form: only declares the lock, pinned by digest, cosign-verified
lox add slack --team T… --channel C… --user U…    # tokens asked at the terminal
lox add telegram --chat ID --from ID               # bot token asked at the terminal
lox import [SUB…]        # merge sub-projects' lockfamily.yaml, strictest routing kept
lox up [--dry-run] [--pin sha256:DIGEST] [--rotate hub|INSTANCE|all]
                  # review, then start; --pin restores a hub version by digest;
                  # --rotate (repeatable) replaces the hub's or a lock's key
lox attach INSTANCE      # a console's start-up questions; detach: Ctrl-P Ctrl-Q
lox approve [--once]     # y, n reason, s, q; o (Ctrl-O + Enter, not macOS): clear values;
                  # r on an expired ticket: approve again
lox mobile pair --name phone    # one-time code, confirmed at this terminal; then lox up
lox mobile list
lox mobile revoke NAME   # then lox up
lox doctor               # hub, locks, keys, socket, network; changes nothing
lox audit verify --data DIR --hub-key-file FILE [--lock INSTANCE=PATH] [--anchors FILE]
                  # the hub's audit chain and every decision's signature

The workspace commands take --file to name another lockfamily.yaml. lockhub

<workspace>/.lockfamily/lockfamily.yaml · lea's agents only read it there · a lock's target, production flag and credentials stay in its own profile

version: 1
hub:
  image: ghcr.io/davidgodefroid/lockhub@sha256:…
  facades: [tty, deck, mobile, slack]   # default: tty, deck
  routing:
    orders: [tty, deck, mobile]         # narrows an instance, never widens
  slack:
    team: T0123
    channel: C0123
    users: [U0123]
  mobile:
    origin: https://hub.example.ts.net  # your TLS proxy or tunnel to 127.0.0.1:8444
    seal_clear: true                    # clear values, end to end to the phone
    require_device: [prod-write]        # only a phone's own signature approves these
    push: true                          # Web Push, no payload
locks:
  orders:
    type: locksql
    image: ghcr.io/davidgodefroid/locksql@sha256:…
    profile: orders                     # the profile the console serves
    allowed_uids: [1000]                # id -u of the account that runs lea
    devices: true                       # pins the paired phones
    reveal: true                        # o / Ctrl-O on the terminal and the deck

lox up writes .lockfamily/up.json for lea and keeps the hub's data, keys and audit log under $XDG_STATE_HOME/lockfamily/ (default ~/.local/state/lockfamily/), out of the workspace. A lockfamily.yaml at the workspace's root (the older layout) is still read, with a warning, until .lockfamily/ exists.

A chat facade never answers a production ticket, whatever its risk class. Chat facades show masked screens only, every agent-supplied string escaped: a chat account is only as safe as the devices signed in to it.

Quick start

Install, start the hub, add your sources.

Linux and macOS · Docker · lockhub v0.4.0 pre-release, lea v0.4.0

# 1. Install the Lock Family: lox, lea, the Locks' launchers and cosign
#    (Homebrew asks you to trust a third-party tap once)
brew trust davidgodefroid/tap
brew install davidgodefroid/tap/lockfamily
#    or into ~/.local/bin, at the tap's versions, each verified with cosign:
#    curl -fsSL https://lockfamily.dev/install.sh | sh
# 2. In lea's projects directory: lea initialises itself and starts the hub
cd ~/projects
lea
# 3. Add each source, one at a time
lox add locksql          # or lockmq, lockfile, lockhttp

Without lea: lox init, then lox add <lock>, then claude + lox approve (in your project or a parent). lox init checks Docker, cosign and the launchers, lists the data sources the project's files name (.env*, compose*.yaml, config/: hints only, never a secret), writes a lockfamily.yaml with the hub alone and runs lox up. lox add TYPE then sets one source up: its questions, the launcher's profile add, init claude and doctor, a short review of that Lock, and the console's own questions (the masked password); a failure, an n or Ctrl-C keeps nothing. A Lock added while lea runs reaches it at lea's next start: lea stop, then lea. Where to run them: for lea, in its projects directory, the only place lea reads .lockfamily/up.json; for a plain claude, in the project or any parent, since each Lock's launcher looks up from the working directory. lockfile is Linux only. lox add · by hand

Know the limits

All of them, the hub included, are before v1: lockhub v0.4.0 and lockhttp v0.7.0 are pre-releases; lea v0.4.0, locksql v0.13.1, lockmq v0.6.1, lockfile v0.6.0 and lockkit v0.10.0 may still change. locklog is coming. The console is the enforcement point and runs hub-attached only; skills and tool descriptions only guide the agent. Masking is best effort. Each project documents what the agent can see and its residual risks in its security model: locksql, lockmq, lockfile, lockhttp, lea. Chat facades never answer production tickets: a chat account is only as safe as the devices signed in to it.
